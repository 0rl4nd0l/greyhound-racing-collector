# One manual On-demand Forecast runbook

This runbook proves one research-only On-demand Forecast. It does not train,
score, promote, calculate value, or authorize betting. Stop at the first
strictly verified `PREDICTION_READY` result. Endpoint and artifact names retain
their existing `prediction` identifiers where required by the API contract.

## 1. Verify the installed source

Work from a clean checkout of the exact reviewed commit. Record both identities:

```bash
git rev-parse HEAD HEAD^{tree}
systemctl --user cat greyhound-operator-ui-r3.service
systemctl --user show greyhound-operator-ui-r3.service \
  -p ActiveState -p SubState -p ExecMainPID
systemctl --user cat shadow-autopilot-odds-capture.service
systemctl --user show shadow-autopilot-odds-capture.service \
  -p ActiveState -p SubState -p ExecMainPID
```

The UI unit must be generated by `bin/operator-ui-deployment generate`, not
hand-edited. Its working directory, binding commit/tree, pinned Python, source
hashes, and generated package hashes must match the reviewed deployment. The
source, collector evidence, producer evidence, and canonical database must be
read-only; only the dedicated Operator UI operations root may be writable.
Use `systemd-analyze verify` on the generated unit before installation. Follow
`DEPLOYMENT.md` for complete generation, secret, installation, and rollback
requirements.

## 2. Admit one exact race

Read the fixed collector current-index packet and its named publication and
refresh report. Do not scan for a substitute packet. Verify all of the
following before opening prediction controls:

- the packet is canonical schema `collector_current_race_index_v2`, fresh
  under the UI policy, pre-jump, and has at most 32 races;
- `current_race_index_publish.status` is `PUBLISHED` and its packet SHA-256
  equals the bytes just read;
- the named refresh report exists, its SHA-256 equals both publication and
  packet references, and its top-level status is exactly `SUCCESS`;
- the refresh report and packet agree on the run, generated time, race IDs,
  jump times, ordered active runners, runner source locators, and runner-set
  hashes;
- the selected race remains sufficiently pre-jump for the complete bounded
  job deadline, and its receipt-only odds source is available;
- the models endpoint has freshly revalidated the catalog, model, manifest,
  config, and schema identities; and
- `GET /operator-ui/api/v1/r3-capability` reports authorized and runtime
  configured at level 2.

Exclude every race with partial metadata. A mixed candidate batch is usable
only when the refresh report itself is `SUCCESS`, its
`current_index_metadata_selection` is `READY_WITH_EXCLUSIONS`, its counts and
exclusions reconcile exactly with `selected_races`, and the published packet
contains only `current_index_races`. Stale, missing, hash-conflicting,
post-jump, ambiguous, or contradictory evidence is an availability stop. Never
reinterpret `METADATA_COVERAGE_INCOMPLETE` as a successful publication.

## 3. Submit once

Authenticate through the existing loopback/private access path. Keep the
cookie jar and CSRF token in a mode-0600 temporary file or memory and remove
them after the session. Never print, log, paste, or commit credentials, cookie
contents, CSRF tokens, or the secret environment file.

Select only values returned by the server:

- exact `race_id` and its displayed ordered runner set;
- model `latest-research` (the validated `market_form_residual_v1` identity);
- configuration `manual-default`; and
- odds source `receipt`.

Submit one `POST /operator-ui/api/v1/prediction-jobs` with the CSRF header and
one newly generated, unguessable idempotency key of at least 16 bytes. Preserve
the request selection and key before transmission. Poll only the returned job
ID through the bounded UI workflow. Do not issue another POST while the first
job is unresolved.

If transport fails after the request may have reached the server, retransmit
only the identical persisted selection and idempotency key. A terminal failure
does not authorize an unchanged retry. A further new POST requires either a
distinct reproduced defect repaired, reviewed, merged, and exactly deployed,
or a genuinely new race after the earlier race ended in a recorded pre-POST
availability stop.

## 4. Verify success

Probabilities may be disclosed only after strict producer and UI verification
returns terminal `PREDICTION_READY`. Preserve the job timeline, request,
claim, attempt, response, authenticated receipt, consume record, result,
bundle manifest, and producer bundle-index entry. Verify:

- exact job, race, jump, ordered runner, runner-set, source, model, manifest,
  config, schema, protocol, process, and history-cutoff identities;
- request/receipt/consume and current-index hashes form one consistent chain;
- every manifest file hash and the logical bundle SHA-256 recompute exactly;
- probabilities are finite, each lies in `[0, 1]`, runner identities are exact,
  and their sum differs from 1 by no more than `1e-12`;
- all source observations and the odds receipt precede the scheduled jump;
- only the dedicated operations/job/audit/protocol/bundle paths changed; the
  canonical racing database, models, configs, frozen experiments, services,
  and source checkout were not written by the prediction job; and
- the process group is gone and no job, browser, or collector lock was deleted,
  stolen, bypassed, or left owned by a dead process.

Record the installed commit/tree, generated hashes, natural collector run,
all live attempts, terminal bundle/hash identities, probabilities, and the
no-unauthorized-write audit in the task evidence packet.

## 5. Roll back the UI gate

If rollback is required, regenerate the reviewed package without `--enable`,
then stop and disable only `greyhound-operator-ui-r3.service` under service
authority. Do not hand-edit the installed unit. Preserve the operations root,
job/audit databases, protocol records, prediction bundles, collector evidence,
current index, locks, and canonical database.
