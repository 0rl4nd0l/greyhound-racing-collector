# Phase 6 evaluation, drift, and promotion

Phase 6 adds a fail-closed evaluation and promotion authority. It does not implement Phase 7 operations, reconciliation, deployment, cutover, or service changes.

## Evidence contract

`EvaluationAuthority` authenticates the champion and explicitly named immutable challengers against the durable registry, bundle manifest, every component artifact, and forecast checksum before evaluation. It also requires every denominator identity to have an append-only Phase-5-derived forward-evaluation relation and verifies the immutable evidence/result artifact bytes and their race, slice, runner, and official-order content. Every model must carry a forecast for exactly the same unique, resolved, evaluation-eligible forward race identities. The race's sealed-evidence checksum must match every forecast. Bundle identity and checksum must remain constant throughout the comparison. Excluded or ambiguous outcomes, incomplete slice identity, invalid runner populations, and mismatched checksums reject the whole comparison. The complete eligible-population identities and evidence/result checksums are recorded separately from the paired subset, making the coverage denominator auditable.

All forecast-quality projections come from the supplied coherent ordered-finish distribution. The scorecard contains ordered-finish NLL, ten-bin win and top-3 calibration, winner MRR, top-3 containment, exact top-2/top-3 order accuracy, and explicit coverage/abstention numerator and denominator semantics. Venue, distance, grade, and field-size slices use the same paired population. Separate flat-unit win/place wagering scorecards exist only when every compared race has sealed immutable win/place odds; they are report-only, cannot place bets, and cannot affect promotion.

The long horizon requires 500 races and versioned venue coverage (initially three venues with 25 races each). The latest 100 paired races and Racing Day views form the short horizon. Short evidence may add a reversal blocker but cannot satisfy a missing long-horizon gate. Paired bootstrap resampling uses races, a recorded seed, and a recorded sample count.

## Promotion and drift

Inconclusive bootstrap evidence or any practical-loss, calibration, coverage, important-slice, sample, venue, or short-reversal failure retains the incumbent. Broad recent degradation is recorded as data/domain drift; champion-only degradation with stable challengers is model drift. Actions request investigation or training separately and never silently train, tune, or promote.

Promotion accepts only an existing complete `canonical_model_bundles` relation and reverifies artifact bytes. Evaluation first seals its complete report as immutable evidence; promotion requires the caller's report bytes and checksum to match that pre-existing durable record, so post-evaluation metric, bootstrap, population, or policy edits fail closed. Promotion records all component checksums, evidence artifact, policy, approver, reason, exact next-day effective Racing Day, and rollback assignment, then appends the first authoritative assignment-history row in the same immediate transaction. The current champion remains live and preserved; Phase 6 never activates the future assignment early. Replay must match the original operation intent. Any failure rolls back the assignment, promotion record, next-day relation, and history together. Training/tuning in the run is an explicit blocker. The Race Collection Service can persist a training request but no Phase 6 API executes training.

Phase 7 probation is represented only as a fail-closed durable input; Phase 6 exposes no method that can manufacture it. Automatic promotion verifies a checksum-backed manifest plus exactly fourteen consecutive successful Racing Day rows, each bearing reconciliation, restart, ordering, and determinism artifact checksums through the day before assignment. Phase 6 does not create operational reconciliation evidence or declare production readiness.

## Root acceptance hardening

Migration 0014 adds explicit immutable run, forecast-artifact, policy, trusted-evaluation, Racing Day schedule, probation-day authentication, next-day assignment, and rollback records. Authoritative evaluation now requires each in-memory projection to match a content-addressed forecast artifact bearing its race, evidence, bundle, computation time, and full ordered distribution. Bundle registration must predate the evaluation run, forecast computation must fall strictly between evidence freeze and result publication, and the report champion must equal the durable current pointer.

Migration 0015 closes the independent acceptance review at the system boundaries. Ordered forecasts must now be emitted by a durable forecast-service run before both the authenticated scheduled start and any result attempt; evaluation can only bind that exact artifact. Forward slice provenance requires exactly one authoritative value for every required field, immutable odds must predate the scheduled start, and candidate training, registration, evaluation, and promotion runs are distinct durable identities. Probation rows are relationally bound to Racing Day IDs, programme checksums, successor order, and the approval day. Promotion and rollback each append an assignment-history entry, so rollback restores the incumbent through audited pointer history rather than an unaudited override. The canonical forecast endpoint may durably request external training, but exposes no training, tuning, registration, or promotion authority.

Migration 0016 replaces the provisional start-time seam with the genuine Phase 2/3 authority chain: the closed Racing Day, immutable programme relation, sealed evidence, and committed `deferred_predictions` artifact. A replay forecast must identify that Phase 3 prediction, use its server-recorded computation time and exact evidence checksum, occur after day close, and precede every result attempt. The service loads each exact immutable registered bundle and derives the full ordered distribution itself; caller-supplied distributions cannot enter this path. Sealed odds are independently checked against the durable `expected_races.scheduled_jump`. `CanonicalForecastApplication` is an in-process typed capability router for forecasts and durable training requests, not proof of a mounted or running HTTP service. It exposes no training or promotion operation; Phase 7 owns process and deployment wiring.

Migration 0017 preserves Phase 2 evidence resolution semantics for evaluation slices: multiple observations remain durable, intrinsic criticality comes from the closed field registry rather than a stored flag, and the highest-authority winner uses the same deterministic value/authority/source/checksum ordering as `normalize_fields`. Thus two agreeing highest-rank observations pass, lower-authority disagreement cannot override them, critical top-rank conflict fails closed, and non-critical top-rank disagreement selects exactly the sealing winner. Each champion or shadow forecast receives a distinct durable service-computation identity and immutable binding, while one service run may compute several forecasts; the Phase 3 prediction is resolved internally as a result-blind timing/evidence anchor rather than accepted as caller authority. It also authenticates policy artifact bytes, ties challenger lineage to the bundle's real registration operation and ordered training/registration/evaluation/promotion runs, and backfills truthful registration runs for immutable bundles that predate this migration using each bundle's own operation and creation time. The migration removes the provisional manual start table and makes append-only assignment history the sole future-day resolver. `next_champion_pointer` is now only a derived latest-history view, so it cannot retain or mutate an alternative challenger authority after rollback. SQL guards enforce full hexadecimal operation/checksum syntax, the exact promotion/rollback chain, and service-request immutability.

Promotion policies are immutable checksum-addressed artifacts. Sealing and promotion reject unknown keys, incomplete horizons/slices/calibration/bootstrap evidence, population checksum disagreement, malformed types, and NaN or infinity. Promotion runs are durable and distinct from evaluation, training, tuning, and candidate registration operations; the assignment operation uses a canonical `OperationId`.

Every Phase 6 mutation binds its complete durable intent into the operation payload used for replay conflict detection. The systematic audit covers run creation, policy registration time, bundle lineage, forecast evaluation-run authority, forecast-service run authority, evaluation seal time, training-request time/run, promotion assignment/approval/approver/reason/probation inputs, and rollback time. Exact retries are idempotent; changing any authority-bearing or durable input under a reused operation ID is a conflict. Broad data/domain drift is authenticated from the report metrics and retains the incumbent even when the challenger remains relatively superior. A zero-loss incumbent also retains deterministically with a finite practical-loss reduction.

The effective assignment is resolved from an authenticated Racing Day successor relation rather than calendar arithmetic. Probation days bind the fourteen predecessor Racing Day identities and programme checksums. A staged rollback is an atomic append-only record whose scheduled resolution restores the preserved incumbent, with replay and conflict protection. The forecast service exposes only durable training-request emission and has no training, tuning, bundle-registration, or promotion method.

## Capability boundary

Tests use small deterministic synthetic ordered distributions (and generated 500-race populations for boundary proof). They prove formulas, gates, transactional behavior, migration paths, and rejection behavior. They are not production evaluation evidence and do not show that fourteen real Racing Days, 500 real paired races, venue coverage, or a production challenger currently exist.
